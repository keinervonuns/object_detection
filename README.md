# PI Detection

Multi-class image classification with real-time camera inference. Train on an
**NVIDIA RTX A2000** (or any CUDA GPU, or CPU), deploy to a **Raspberry Pi 5**
that runs the live feed and drives a **4-bit GPIO LED** display.

The workflow: collect images → split train/val → train → copy the model to the
Pi → run detection with GradCAM + OmniXAI (LIME) explainability and region
masking.

Everything lives under [`Torch/`](Torch/).

## 1. Choose your setup

You can train on a GPU machine and copy the model to the Pi, or train directly on
the Pi (CPU only — much slower). Both use the same code and the same `Torch/`
directory.

| | Option A — train on a GPU machine *(recommended)* | Option B — everything on the Pi |
|---|---|---|
| Training | Windows / Linux machine with a CUDA GPU (e.g. RTX A2000) | Raspberry Pi 5, **CPU only** |
| Speed | Minutes per epoch | Many minutes per epoch |
| Model transfer | `scp`/`rsync` `models/best_model.pth` to the Pi | — |
| Inference | Pi (GPIO LEDs) | Pi (GPIO LEDs) |

Do the environment setups you need from [section 2](#2-environment-setup).

## 2. Environment setup

Python 3.10+ everywhere (developed on 3.10–3.13; the Pi 5 runs 3.13).

### 2.1 GPU training machine — Windows

PyTorch on Windows ships a CUDA-enabled wheel by default for recent versions.

```powershell
cd Torch

# Create and activate a virtual environment
python -m venv venv
venv\Scripts\Activate.ps1
#   If PowerShell blocks the script, allow it for this session:
#   Set-ExecutionPolicy -Scope Process Bypass

python -m pip install --upgrade pip
pip install -r requirements.txt

# Optional — OmniXAI explanation reports (the `s` key writes an HTML file).
# Use the narrow extras and re-apply the pins afterwards (see the note below).
pip install "omnixai[vision,plot]"
pip install -r requirements.txt
```

Verify the GPU is picked up:

```powershell
python -c "import torch; print(torch.cuda.is_available())"
```

Windows notes:
- If the `DataLoader` errors out with worker/`spawn` problems, set
  `NUM_WORKERS = 0` in **config.py**.
- Symlinks need **Developer Mode** (see [step 5](#5-split-into-train--val)); set
  `COPY_FILES = True` instead if you'd rather skip that.

### 2.2 GPU training machine — Linux

```bash
cd Torch
python3 -m venv venv
source venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
pip install "omnixai[vision,plot]"   # optional — see the omnixai note below
```

**GPU:** if `torch.cuda.is_available()` is `False`, install the CUDA wheel
matching your driver from <https://pytorch.org/get-started/locally/>. The CUDA
toolkit / NVIDIA driver itself must be installed separately
(<https://developer.nvidia.com/cuda-downloads>).

### 2.3 Raspberry Pi 5

Copy the whole project to the Pi. GPIO (`RPi.GPIO`) lives in the **system**
Python, while the heavy packages come from the venv.

```bash
cd ~/pidetection/Torch     # wherever you put the project

# Create the venv with the same Python as the system python3 (3.13 on the Pi 5)
python3 -m venv venv
source venv/bin/activate

pip install --upgrade pip
pip install -r requirements.txt
pip install RPi.GPIO
deactivate
```

> `run.py` adds `venv/lib/python*/site-packages` to the **system** interpreter's
> path at launch, so `sudo python3 run.py` gets `RPi.GPIO` from the system and
> `torch` / `cv2` from the venv.

`omnixai` is optional everywhere: it is imported lazily and guarded, so if it is
missing the live feed still runs with real-time GradCAM and the full UI — you
only lose the HTML report written by the `s` key. The rest of `requirements.txt`
(torch, torchvision, opencv, numpy) is required.

> **Installing `omnixai`:** use `pip install "omnixai[vision,plot]"`, **not**
> `omnixai[all]`. `[all]` also pulls the NLP/BentoML stacks, and the vision
> extras install **`opencv-python-headless`**, which has no GUI functions —
> `cv2.imshow` / `cv2.namedWindow` would fail. Re-run
> `pip install -r requirements.txt` afterwards so the pinned `opencv-python` and
> `scikit-learn>=1.3` win (omnixai's 2023-era release can otherwise downgrade
> them).

## 3. Configure your classes

Open **config.py** and edit the `CLASSES` dict to match your object names:

```python
CLASSES = {
    "background": 0,
    "green_cube": 1,
    "blue_cube": 2,
    "pink_cylinder": 3,
    "silver_cylinder": 4,
    "silver_cube": 5,
    "gray_cuboid": 6
}
```

**This dict defines your classes — you don't create the folders by hand.** The
keys must exactly match the sub-folder names under `source/`, and step 4 creates
those folders *from this dict*. Keep `CLASSES` identical on the training machine
and the Pi.

The **values are the number sent to the GPIO LEDs** when that class is predicted
(see [GPIO LED output](#gpio-led-output)). Keep them unique (two classes sharing
a number look identical on the LEDs) and within `0–15` — they are not validated,
so a value above `15` produces a 5-bit string, overruns the 4-pin list, and
silently lights the wrong pattern. Keep the numbers stable once your wiring is
built.

> **Folder discovery is not driven by this dict.** `setup_data.py` splits whatever
> folders it finds in `source/`, including ones missing from `CLASSES`. `train.py`
> prints a NOTE if the detected folders differ from `config.CLASSES` — since it
> compares the *alphabetically sorted* folder list against the *insertion order*
> of the dict, that NOTE prints on this project even when the classes are correct
> (the order differs, the set doesn't). `run.py` looks classes up by name with
> `numbers.get(class_name, 0)`, so a class present in the model but absent from
> `CLASSES` outputs `0` on the LEDs.

## 4. Collect images

Create the folder skeleton from `CLASSES`:

```bash
python setup_data.py --init
```

Then drop images into each `source/<class>/` folder:

- Supported formats: `.jpg` `.jpeg` `.png` `.bmp` `.webp` `.tiff`
- Aim for **at least 50–200 images per class**
- More data beats a bigger model; vary angles, distances, lighting, backgrounds

> **Shortcut:** `python capture_images.py` opens the webcam and saves frames
> straight into `source/<class>/` as `00000.jpg`, `00001.jpg`, …  
> Controls: `SPACE` save · `c` auto-save every 500 ms · `n` / `p` next / previous
> class · `q` quit. Classes cycle in `config.CLASSES` order. It needs a display —
> run it on the machine that has the webcam.

## 5. Split into train / val

```bash
python setup_data.py
```

Shuffles and splits your source images (wipes and rebuilds `data/` on each run):

| Split | Default | Controlled by |
|-------|---------|---------------|
| Train | 80 %    | `VAL_SPLIT` |
| Val   | 20 %    | `VAL_SPLIT` |

| Setting | Default | Description |
|---------|---------|-------------|
| `VAL_SPLIT` | `0.2` | Fraction held out for validation |
| `SPLIT_SEED` | `42` | Random seed — change for a different split |
| `COPY_FILES` | `False` | `False` = symlinks (saves disk); `True` = copies |

> On Windows, symlinks need **Developer Mode** (`Settings → System → For
> developers → Developer Mode`); if it fails the script falls back to copying.
> On the Pi keep `COPY_FILES = False` — symlinks save space on the 32 GB card.

## 6. Train

### 6.1 On a GPU machine (recommended)

With the venv activated, from `Torch/`:

```bash
# Windows: venv\Scripts\Activate.ps1     Linux: source venv/bin/activate
python train.py
```

1. Loads `data/train` and `data/val`
2. Fine-tunes the ImageNet-pretrained `BACKBONE` on your classes
3. Augments each epoch: crop, flip, rotation, colour jitter, random erase, MixUp
4. Uses **mixed precision (AMP)** — faster and lower VRAM on the A2000
5. Saves the best checkpoint to `models/best_model.pth`
6. Stops early after `EARLY_STOP` epochs without improvement
7. Writes `models/training_curves.png`, `models/classification_report.txt`,
   `models/training_history.json`

| Setting | Default (A2000) | Notes |
|---------|-----------------|-------|
| `BACKBONE` | `resnet50` | Also `efficientnet_b0`, `efficientnet_b2` |
| `IMG_SIZE` | `224` | Native size for all backbones |
| `BATCH_SIZE` | `32` | Lower to `16` on CUDA out-of-memory |
| `NUM_EPOCHS` | `50` | Early stopping may end it sooner |
| `LEARNING_RATE` | `3e-4` | AdamW learning rate |
| `WEIGHT_DECAY` | `1e-4` | AdamW weight decay |
| `SCHEDULER` | `cosine` | Or `step` (`STEP_LR_DECAY` / `STEP_LR_STEP`) |
| `EARLY_STOP` | `8` | Epochs without improvement before stopping |
| `LABEL_SMOOTHING` | `0.1` | Helps on small datasets |
| `USE_AMP` | `True` | Keep on for the A2000 |
| `MIXUP_ALPHA` | `0.2` | MixUp strength; `0` disables |
| `NUM_WORKERS` | `4` | Set to `0` if the DataLoader errors (Windows) |

### 6.2 On the Raspberry Pi (CPU only)

The Pi 5 has no CUDA GPU, so training runs on the CPU — it works, but expect
minutes per epoch. Use the smallest backbone and a small batch.

Edit **config.py** on the Pi:

```python
BACKBONE    = "efficientnet_b0"   # fastest backbone
BATCH_SIZE  = 8                   # 4 if you run out of RAM (8 GB total)
NUM_WORKERS = 2
USE_AMP     = False               # AMP is CUDA-only (ignored on CPU anyway)
PIN_MEMORY  = False               # there is no GPU to pin memory for
```

Then, with the venv activated:

```bash
source venv/bin/activate
python train.py
```

Notes for Pi training:
- `train.py` finishes by opening a matplotlib window. On a headless Pi it only
  prints a warning — the plot is still saved to `models/training_curves.png`. Run
  from the Pi's desktop, or over `ssh -X`, if you want to see it.
- Keep the dataset small (a few hundred images) so a run finishes in reasonable
  time; otherwise train on a GPU machine and
  [copy the model over](#7-transfer-the-model-to-the-pi).
- The output is the same `models/best_model.pth` as on a GPU machine — the exact
  file the live feed loads.

## 7. Transfer the model to the Pi

Inference only needs **`models/best_model.pth`**: it stores the class list, the
backbone name and the weights, so it is self-contained. Copy that one file from
the training machine to the Pi.

Create the target folder on the Pi first (it is git-ignored and may be absent):

```bash
# on the Pi
mkdir -p ~/pidetection/Torch/models
```

**From Linux/macOS (training machine):**

```bash
# scp
scp Torch/models/best_model.pth pi@raspberrypi.local:/home/pi/pidetection/Torch/models/

# or rsync (resumable, shows progress)
rsync -avP Torch/models/best_model.pth pi@raspberrypi.local:/home/pi/pidetection/Torch/models/
```

**From Windows (PowerShell, built-in OpenSSH `scp`):**

```powershell
scp .\Torch\models\best_model.pth pi@raspberrypi.local:/home/pi/pidetection/Torch/models/
```

Replace `pi@raspberrypi.local` with your Pi's user and host (or IP). Alternatives:
copy the file to a USB stick, or share the model folder over the network (e.g.
Samba).

> Re-train on the GPU machine and repeat this copy to update the Pi's model. You
> can also copy the whole project once and thereafter push only
> `models/best_model.pth` — the code and `requirements.txt` rarely change.

## 8. Run detection

`run.py` is the single entry point. GPIO LED output is **on by default**; pass
`--no-gpio` to disable it.

### 8.1 Everything on the Pi (with GPIO LEDs)

The Pi needs the trained model from [step 7](#7-transfer-the-model-to-the-pi), a
camera connected, and the LEDs wired (see [GPIO LED output](#gpio-led-output)).

```bash
sudo python3 run.py
```

On startup `run.py`:

1. parses `--no-gpio` and, when GPIO is enabled, initialises `RPi.GPIO`
   **before** `torch` / `cv2` are imported (importing them first can interfere
   with GPIO setup),
2. adds the project venv's `site-packages` to `sys.path` (so `torch` / `cv2`
   come from the venv while `RPi.GPIO` comes from the system),
3. runs the feed.

`sudo` is required for GPIO access. If GPIO init fails the script warns and
continues with the LEDs disabled (pass `--no-gpio` to skip the warning). All
paths are absolute (resolved from `config.BASE_DIR`), so the project can live
anywhere and be run from any directory.

Running under `sudo` needs X access — run from the Pi's own desktop, or allow it
once with `xhost +local:root` (or start the process with `sudo -E`).

### 8.2 On the training machine (no GPIO)

```bash
# Windows: venv\Scripts\Activate.ps1     Linux: source venv/bin/activate
python run.py --no-gpio
```

Handy for testing the model on the machine that trained it, without a Pi.

Either way, the camera is opened as **index 0, V4L2, MJPG, 1920×1080, buffer 1**,
in a fullscreen window. A second capture handle (index 1) is opened briefly at
startup only to read the frame size for the region default.

**Keyboard controls:**

| Key | Action |
|-----|--------|
| `G` | Toggle GradCAM heatmap overlay |
| `S` | Save current frame + OmniXAI HTML report |
| `E` | Enter / exit region edit mode (saves the rectangle on exit) |
| `R` | Reset FPS counter |
| `H` | Print help to terminal |
| `Q` | Quit — or, in region edit mode, save the region and exit edit mode |

**In region edit mode:**

| Key | Action |
|-----|--------|
| Arrows | Move the active border (`SHRINK` moves inward, `EXPAND` outward) |
| `S` | Toggle expand / shrink (outside edit mode `s` *saves*) |
| `Z` | Undo the last border move |
| `C` | Reset the region to the full frame |
| `E` / `Q` | Confirm, save to `regions/region_config.ini`, leave edit mode |

**On-screen display:** top banner (class + confidence bar), side panel (top-3
probabilities), bottom bar (FPS, GradCAM status, key hints), and a dimmed
surround showing the area outside the detection region (yellow while editing,
green otherwise).

> The class label only changes after it has been stable for `DISPLAY_SECONDS`
> (default `1.0`) to stop flicker; confidence keeps updating meanwhile.

## Detection region

Only the rectangle in `regions/region_config.ini` is fed to the model; everything
outside is zeroed before inference and dimmed on screen.

```ini
[region]
left = 1056
top = 504
right = 1696
bottom = 744
```

Press `e`, move the borders with the arrow keys, then `e` again to save. The
rectangle is clamped to the frame and can't shrink below 40 px per side.

## GPIO LED output

The predicted class is broadcast as a **4-bit binary number** on four GPIO pins,
updated once per inference in the background thread.

| Pin (BCM) | Bit | Value |
|-----------|-----|-------|
| 17 | bit 0 | 1 (LSB) |
| 27 | bit 1 | 2 |
| 22 | bit 2 | 4 |
| 23 | bit 3 | 8 (MSB) |

The number comes from the `CLASSES` dict, e.g. `blue_cube → 2` lights pin 27 only.

**Wiring (active-LOW):** 3.3 V → LED anode; LED cathode → ~220 Ω resistor → GPIO
pin. The pin sinks the current, so a bit is pulled `LOW` to switch it on.

**The pins are driven active-LOW** — a bit is `LOW` for `1` and `HIGH` for `0`,
and "off" sets all four pins `HIGH`. `tests/test_led.py` uses the same convention
in both modes, so a wiring check with it matches what the live feed does. Verify
with `tests/test_led.py` before running the full pipeline.

## Tests

Standalone hardware sanity checks live in `tests/` (run them from `Torch/`):

```bash
python tests/test_camera.py            # live preview + actual resolution
python tests/test_led.py               # single LED on GPIO 17
python tests/test_led.py --mode binary # 4-LED binary display (0–15)
```

- `test_camera.py` — confirms the camera index and resolution; press `q` to quit.
- `test_led.py --mode single` — blinks one LED on GPIO 17 (gpiozero → mock →
  RPi.GPIO fallbacks).
- `test_led.py --mode binary` — displays `0–15` on the LED array; type a value,
  `16` to cycle through all of them, `q` to quit. GPIO access normally needs
  `sudo`.

## Changing the camera

```python
cap = cv2.VideoCapture(0, cv2.CAP_V4L2)
cap.set(cv2.CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*"MJPG"))
cap.set(cv2.CAP_PROP_FRAME_WIDTH,  1920)
cap.set(cv2.CAP_PROP_FRAME_HEIGHT, 1080)
cap.set(cv2.CAP_PROP_BUFFERSIZE, 1)
```

Change the first argument (`0` → `1`, `2`, …) for a different device. `CAP_V4L2` is
Linux-only — drop it on Windows/macOS. `run.py`, `capture_images.py` and
`tests/test_camera.py` share these settings, so update all three together.

There is also a **second** capture at index `1`, opened only to read the frame
dimensions used as the region default; if it fails it quietly falls back to
`1920×1080`. Run `python tests/test_camera.py` to confirm the index and resolution.

> **On the Pi:** the feed opens a **V4L2** device, so a **USB webcam** works out
> of the box. To use the CSI ribbon camera, enable the V4L2 compatibility layer
> (`libcamera` → `bcm2835-v4l2`) so it appears as `/dev/video*`.

## Switching backbone

Edit `BACKBONE` in **config.py**, then re-train:

| Backbone | VRAM | Speed | Accuracy |
|----------|------|-------|----------|
| `efficientnet_b0` | ~2 GB | Fastest | Good |
| `efficientnet_b2` | ~3 GB | Medium | Better |
| `resnet50` | ~4 GB | Medium | Comparable |

`efficientnet_b0` is the pick for Pi (CPU) training; `resnet50` / `efficientnet_b2`
are for the GPU machine. `run.py` rebuilds the architecture from the `backbone`
field stored in the checkpoint, so no change is needed there.

## Tips for better accuracy

- **Vary your source images** — angles, distances, lighting, backgrounds
- **Balance your classes** — similar image counts per class
- **Include a `background` class** — scenes with no target object reduce false positives
- **More data beats a bigger model** — double your images before switching backbone
- **Check the classification report** — low per-class recall means that class needs more images

## Troubleshooting

| Problem | Fix |
|---------|-----|
| `CUDA out of memory` | Lower `BATCH_SIZE` to `16` or `8` |
| `torch.cuda.is_available()` is `False` | Install the CUDA wheel matching your driver from pytorch.org |
| `Import torch could not be resolved` (VS Code) | Select the venv interpreter: `Ctrl+Shift+P` → *Python: Select Interpreter* → `Torch/venv` |
| PowerShell won't run `Activate.ps1` | `Set-ExecutionPolicy -Scope Process Bypass`, then re-run it |
| `Cannot open camera` | Check index/resolution with `python tests/test_camera.py`; the camera uses `CAP_V4L2` (Linux only) |
| `No trained model found` | Train first (`python train.py`) or [copy the model to the Pi](#7-transfer-the-model-to-the-pi) |
| Symlink error on Windows | Enable Developer Mode or set `COPY_FILES = True` |
| Very low accuracy | Add more images; check folder names match `CLASSES` exactly |
| `NUM_WORKERS` errors on Windows | Set `NUM_WORKERS = 0` in config.py |
| Training on the Pi is extremely slow | Expected — use `BACKBONE = "efficientnet_b0"`, `BATCH_SIZE = 8`, or train on a GPU machine instead |
| `⚠ GPIO unavailable … LED output disabled` | Run with `sudo python3 run.py` on the Pi, or pass `--no-gpio` on a machine without GPIO |
| `Matplotlib` plot window doesn't appear on the Pi | Headless Pi — the plot is still saved to `models/training_curves.png` |
| LEDs light up inverted | Wiring is active-HIGH — the code drives active-LOW (bit = pin `LOW`); see [GPIO LED output](#gpio-led-output) |
| `cannot open display` under sudo | Allow X access: `xhost +local:root` (or run with `sudo -E`) |
| `omnixai` explainer unavailable | Only needed for `s`; GradCAM still works |
| Region has no effect | INI missing → press `e` to draw one and save |
| Detects objects outside the region | Press `e` then `c` to reset, or re-save a wider rect |
